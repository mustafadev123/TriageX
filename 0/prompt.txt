# TriageX — Approve Phase 2: Deterministic Simulation Engine

Phase 1 is approved and complete. GitHub and Entire checkpoints are synced.

## Objective

Build a reproducible hospital surge simulation that supports our central demo:

**One surge. Two futures.**

The same synthetic patient arrivals and initial hospital conditions must produce two comparable tracks:

- **Baseline:** Ordinary reactive hospital operations, including realistic diversion.
- **With TriageX:** The same operations, plus explicitly approved and confirmed interventions.

No artificial improvements, hardcoded outcomes, or hidden advantages.

## Implementation requirements

### 1. Hospital network

Model the five Atlanta hospital locations already defined in our plan.

Use synthetic staffing, treatment-space capacity, arrivals, and service times. Do not represent these values as actual hospital conditions.

### 2. Simulation engine

Implement the planned 15-minute tick engine, with a 24-hour simulation horizon and support for displaying a six-hour demo window.

Use deterministic random generation and stable ordering.

The engine must support identical replay from the same scenario, seed, and intervention list.

### 3. Two simulation tracks

Track A and Track B must be identical when no interventions exist.

They must remain identical until a TriageX intervention actually becomes effective.

### 4. Staffing intervention

Use the Phase 0 plan's 45-minute simulated staffing lead time.

A staff confirmation may increase staffed capacity only when physical treatment spaces are available.

The intervention must not instantly reduce queues when the confirmation arrives.

### 5. Surge scenarios

Implement the four planned synthetic scenarios:

- I-85 Multi-Vehicle Pileup
- Big Game Downtown
- Summer Heat Wave
- Respiratory Wave

Prioritize making the I-85 scenario credible and deterministic.

### 6. Forecasting

Implement the planned two-hour-ahead projection using only information available at the current simulated time.

Forecasts must not inspect future patient arrivals.

Keep forecasts separate from actual future outcomes.

### 7. Computed metrics

Calculate all results from simulation state and patient events.

Include:

- Hospital saturation
- Queue lengths
- Patient waiting times
- Ambulance handoff waiting hours
- Diversion events
- Staff utilization
- Intervention effectiveness

Never hardcode percentage improvements.

### 8. Demo-specific requirements

The engine must support:

- A shared timeline for both tracks.
- A visible intervention approval time.
- A 45-minute simulated lead-time window.
- A shift-active marker.
- Recalculation of Track B after a confirmation.
- A six-hour view of the complete scenario.

The eventual UI should be able to show two curves separating only after an intervention becomes effective.

### 9. Testing

Write meaningful automated tests covering:

- Deterministic replay.
- Baseline equality without interventions.
- No effect before intervention activation.
- Staffing constrained by physical capacity.
- Correct ambulance handoff calculations.
- Forecast isolation from future arrivals.
- Consistent results across scenarios.

Run pytest, Ruff, and any other applicable checks.

## Hackathon Demo and Pitch Priority — Critical

TriageX is being built for a live hackathon presentation. Our primary goal is to demonstrate a compelling, visually clear, end-to-end hospital surge coordination system.

Every backend decision should support the following experience:

**Surge predicted → Human approves outreach → Staff confirms → Intervention becomes active → Two simulated futures visibly diverge → Measurable impact appears.**

Design the API responses so the frontend can deliver this entire experience on a single screen without unnecessary navigation or waiting.

Specifically:

1. **Cinematic demo progression:** Return the data needed for a smooth timeline replay, including hospital status transitions, forecast alerts, approval events, confirmation events, staffing lead-time bands, shift-start markers, and comparison curves.

2. **Strong visual storytelling:** Make it straightforward for the frontend to animate the transition from identical baseline and intervention curves to visibly different outcomes after the intervention becomes active.

3. **Hero metrics:** Prioritize ambulance handoff hours, patient waiting time, and hospital recovery. Return computed absolute differences and percentage changes so the frontend doesn't need to calculate them.

4. **Instant interaction:** Aim for the confirmed staffing response to trigger an updated comparison in under 200 ms locally. Measure the actual latency rather than assuming it.

5. **Six-hour demo window:** Provide a ready-to-render six-hour timeline for the I-85 scenario, while preserving the underlying 24-hour simulation.

6. **Single-screen presentation:** Design response schemas for a dashboard containing an Atlanta hospital map, synchronized comparison charts, a live coordination feed, and one prominent impact metric.

7. **Reliable demo reset:** Support returning the application to the same initial scenario and timeline so we can rehearse the presentation repeatedly.

8. **Presentation-friendly event labels:** Provide concise event titles such as "Surge Predicted," "Outreach Approved," "Staff Confirmed," and "Shift Active."

9. **Authentic results:** All metrics must come from the simulation. Never fabricate improvements, modify historical results, or make the intervention appear effective before its simulated activation time.

10. **Keep technical limitations out of the main demo narrative:** Present the strongest verified capabilities and computed results prominently. Keep engineering diagnostics available for development and judge Q&A, rather than cluttering the presentation screen.

The desired result is not simply a functioning API. It is an API specifically designed to power a memorable, polished, 90-second live demonstration.
